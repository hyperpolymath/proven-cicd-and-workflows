= Interim CI/gate

The Branch-Floor rulesets on `main` of some estate repositories require the commit-status
context `CI/gate`, and nothing emitted it. This is a swappable interim gate that does. A later
A3 `estate-gate` replaces it by changing one pin and one context name in each caller.

* Reusable: `.github/workflows/ci-gate.yml` (job id `gate`).
* Caller: `templates/ci-gate-caller.yml` (`__CICD_SUITE_SHA__`, DE-ONBOARDED from `actions.lock` like the Rust CI caller). The suite gates itself with `.github/workflows/ci-gate-caller.yml` (context `CI / gate`, the local reusable).
* Sweep: `scripts/ci-gate-sweep.sh`, run by the reusable on `schedule` and `workflow_dispatch`.
* Verdict (pure, offline): `scripts/ci-gate-verdict.sh`; profile validator `scripts/validate-ci-gate-profile.sh` with `profiles/ci-gate/validate.jq`.
* Required-check lists: `profiles/ci-gate/<owner>/<repo>.json`, derived as recorded in link:../profiles/ci-gate/README.adoc[profiles/ci-gate/README.adoc].
* Controls: `tests/ci-gate.sh` (run by the `Composite shell contract` job of `code-hygiene-self-test.yml`).

== Design in one paragraph

The caller triggers on `workflow_run` (`completed` and `in_progress`, any workflow but its own), on `schedule` (minutes 7, 22, 37 and 52 of every hour) and on `workflow_dispatch`; see "Sweep" below for the last two. The `in_progress` event, which GitHub also sends when a run is rerun, makes the gate publish `pending` over a stale `success` while any run of the commit other than the gate's own is active (a rerun of an older, superseded run included), approximating a native required check; the evaluator triggered by `completed` then writes the verdict, subject to the residual last-writer-wins limit below. GitHub runs
`workflow_run` workflows from the default branch, so a pull request cannot edit the caller, its
pin or its list. The reusable reads the profile for `github.repository` from this suite at
`job.workflow_sha`, lists the workflow runs of the head commit (all pages), keeps the newest run per workflow and event without the gate's own, reads the jobs of the latest attempt of each, runs
the verdict script and posts one commit status. It is a commit status, not a check run,
because a job in a reusable workflow gets the check-run name `<caller job> / <called job>`,
which can never equal `CI/gate`.

== Verdict rules

Only GitHub Actions jobs are read. Third-party checks (SonarCloud, CodeRabbit, GitGuardian, CodeQL from github-advanced-security) are out of scope: they are neither counted nor able to spoof a name.

. Workflow runs of the head commit are listed (all pages). The gate's own runs (by workflow name) are dropped; per (`workflow_id`, `event`) only the newest run (highest `id`) is kept. For each kept run its jobs are read with `filter=latest` (all pages), so an earlier attempt of a rerun is discarded.
. A profile entry is an identity, `{job, workflow}` (profile `schema_version` 2): the job display name and the workflow file (`path` of the run) that produces it. An entry is satisfied only if a kept run with that `path` exists and *every* job with that exact `name` in those runs is `completed` with conclusion `success`. Two workflows producing one display name are two entries, both required, so a second producer that never ran is a failure. Two jobs that share a name inside one run are both required; none is chosen by highest `id`.
. Any required-name job completed with another conclusion (`failure`, `cancelled`, `timed_out`, `skipped`, `neutral`, `action_required`, `stale`, none) is a *failure* at once. `skipped` and `neutral` are not passes.
. Else, if any workflow run of the commit other than the gate's own (kept or superseded, so a rerun of an older run counts) is still `queued`, `in_progress`, `waiting`, `requested` or `pending`, the verdict is *pending* (`waiting for N workflow runs: ...`), even when every required name already has a passing job, because a later producer of the same name may still fail. Once the oldest kept or active run is older than `timeout_minutes` it is a *failure* (`timed out after N min: ...`).
. Else (nothing is active): an entry with no kept run or no job is a *failure* (`never reported: <workflow file>:<job>`), a required name whose job never completed is a failure, and otherwise the verdict is *success*.
. A malformed or wrong-repository profile, an empty list, a list naming the gate's own context, a missing `job.workflow_sha`, any API error, malformed input, or any event other than `workflow_run`, `schedule` and `workflow_dispatch` is a failure, never pending and never success.

The status description is at most 140 characters (truncated with an ellipsis); the step summary
carries the full table. `scripts/ci-gate-verdict.sh` exits 0 for success, 3 for pending and 1
for failure and for every error.

== Publishing and the settle guard

Reading, evaluating and publishing is `scripts/ci-gate-publish.sh` (fetched from the suite at `job.workflow_sha` like the other scripts; it talks to GitHub only through `gh`, so `tests/ci-gate.sh` drives it with a fake `gh`). The caller has no `concurrency:` block: per-SHA serialisation would hold the `in_progress` caller behind a running evaluation that then writes a stale success.

. The first step after input validation, before any suite file is fetched, POSTs `pending` (`re-run started: <workflow name>`) when the event action is `in_progress`. It needs only `gh`, the repository, the head SHA and the context. Every later write is a fresh evaluation, so this early pending never hides a verdict.
. The publisher snapshots the workflow runs of the commit and fingerprints them: the sorted (`id`, `status`, `conclusion`, `run_attempt`, `updated_at`) of every run but the gate's own. It reads the jobs and computes the verdict.
. Guard: just before the POST it fetches the runs again. If the fingerprint moved it does not write and starts a new round.
. Post-write verification: after each POST it fetches the runs once more. If the fingerprint moved since the snapshot it re-evaluates and writes again.
. At most 5 rounds in all. If the runs are still changing after 5 rounds, the last write is `pending` (`runs still changing`), never success. The guard and the verification apply to every state. They narrow, but do not close, the window in which a delayed evaluator leaves a stale state (success, pending or failure); see the residual limit below.
. Any API or input error posts a failure status and exits non-zero.

*Residual limit.* GitHub commit statuses are last-writer-wins and the statuses API has no compare-and-swap. A delayed evaluator can therefore publish a stale state, success included: one that was paused between its final check and its POST overwrites a newer status. The post-write verification shortens that window and does not remove it. This design guarantees neither convergence nor a time bound. Two stale outcomes remain possible. (1) Fail-open: a stale `success` stands until a later evaluator overwrites it; every later change of a workflow run raises a `workflow_run` event whose evaluator writes again, but nothing bounds when that happens. (2) Fail-closed: a delayed evaluator's final `pending` (for example "runs still changing") can land after another evaluator's `success`, and if no workflow run changes afterwards it stays. The branch then remains blocked until someone re-runs a workflow on the commit, which raises a fresh evaluation. Neither outcome is detected automatically. This is a residual limit of the interim gate, not something this design proves away. Removing it needs a compare-and-swap that the statuses API lacks; the A3 `estate-gate` design (signed envelopes) is the place to do that.

== Sweep (schedule and workflow_dispatch)

On `schedule` and `workflow_dispatch` there is no triggering run, so the reusable sweeps `github.repository` instead of evaluating one commit. `scripts/ci-gate-sweep.sh` (fetched from the suite at `job.workflow_sha` like the other scripts; it uses only `gh`, so `tests/ci-gate.sh` drives it with the fake `gh`):

. lists the open pull requests (`/repos/{repo}/pulls?state=open&per_page=100`, every page) and the head of the default branch;
. de-duplicates the head SHAs (two pull requests with one head, or a pull request at the default branch head, are one evaluation);
. above 100 distinct SHAs it evaluates the 100 most recently updated, counting the default branch head as the most recently updated, and prints a `::warning::` naming how many were not evaluated; the step summary table names them too;
. runs exactly the guarded publisher (`scripts/ci-gate-publish.sh`) once per SHA, with no early `in_progress` pending, so each SHA gets the same settle guard, post-write verification and fail-closed rules as a `workflow_run` evaluation;
. never stops on one SHA: a failure or an API error on one SHA is recorded and the others are still evaluated;
. writes a table (commit, source, state, description) to `$GITHUB_STEP_SUMMARY`, and exits non-zero at the end if any SHA ended in `failure` or `error`, or if the pull request list or the default branch head could not be read. `pending` and `success` are not red.

The event is still refused for anything except `workflow_run`, `schedule` and `workflow_dispatch`. The job needs `pull-requests: read` in addition to `statuses: write`, `actions: read` and `contents: read`: *the caller must grant it*, or the pull request listing fails and the sweep is red. A sweep writes statuses for pull request heads from forks too (the statuses API is keyed by commit in the base repository); it reads metadata only and never checks out or runs their code.

== Workflow acceptance contract

[cols="1,4",options="header"]
|===
|Field |Statement
|Events |`workflow_run` (one commit), `schedule` and `workflow_dispatch` (a sweep of every open pull request head and the default branch head, at most 100 SHAs). Any other event is refused: red job, no status. (default `CI/gate`; the one swappable name; `[A-Za-z0-9][A-Za-z0-9._/-]{0,127}`), `timeout_minutes` (default 180). The repository is never an input: the profile is selected by `github.repository`. No `secrets:`.
|Side effects |On an `in_progress` event a first `POST /repos/{repo}/statuses/{head_sha}` of `pending`; then a verdict POST, repeated if the settle guard or the post-write verification finds the runs moved (at most 5 rounds, then `pending` "runs still changing"), with the context, state, description (at most 140 characters) and a `target_url` to the gate run; a step summary. Nothing else is written. Pending is a normal wait for the next `workflow_run`.
|Permissions |Granted by the caller: `statuses: write`, `actions: read`, `contents: read`, `pull-requests: read` (read only by the sweep). The reusable asks for exactly these and no more.
|Subjects |The head commit of the completed workflow run, in the repository the caller lives in. Required checks are Actions job names in the suite's profile for that repository. Third-party checks are out of scope.
|Failure and refusal |Any event other than `workflow_run`, `schedule` or `workflow_dispatch`: refused, red job, no status. A sweep that ends with any SHA in failure or error is red. A missing, empty, malformed, wrong-repository or self-naming profile, an empty `job.workflow_repository` or `job.workflow_sha`, or any API error: failure; the job is red and a final step posts a failure status if none was published. A failed verdict also exits the job non-zero. No code from the consumer or a pull request is checked out or executed, and no `${{ }}` reaches a `run:` script (values travel through `env:`).
|Controls |`tests/ci-gate.sh`: positive control (all present and successful); negatives with exact states for a required name with no job (headline: nothing active), an unrelated run still active (pending) and past the timeout (failure), two producers of one name with one still queued (pending), two same-named jobs in one run with one failing, superseded runs, a second attempt, the gate's own run ignored, failed/cancelled/skipped/neutral/timed_out/action_required/stale/startup_failure jobs, malformed inputs, description length;; the sweep (a stale success corrected to failure, a stuck pending corrected to success, SHA de-duplication, the cap and its warning, one SHA's API error not stopping the others, the non-zero exit); the validator rejects malformed JSON, wrong repository, empty list, the gate's own contexts, duplicate members and unclean names; the shipped profiles validate and are JCS-serialised; static guards (no `${{` in any `run:`, no `uses:`, `workflow_call` only, template has no `pull_request` trigger, no `concurrency` block, both `workflow_run` types, `schedule`, `workflow_dispatch` and `pull-requests: read`; the suite's own caller).
|Receipt |The commit status itself (context, state, description, `target_url` to the run), and the step summary of the run: the verdict, the commit, the profile and the suite commit it was read at, and one row per required check. Offline control output is in the self-test job log. A sweep also leaves its table in the step summary.
|===

== Known limits

* Bootstrap: see "Bootstrap" below.
* A repository instantiated from the template gets the caller but no suite profile: the gate fails closed until a profile is added here.
* Anyone with write access can post a `CI/gate` status by hand; the rulesets do not pin an integration.
* A required check that is path-filtered or conditional would fail the gate as `never reported` on a pull request that does not trigger it. Profiles list only checks that run unconditionally on both pull requests and pushes to `main`; re-derive a profile when a workflow's triggers change.
* End-to-end behaviour on GitHub is not demonstrated until a caller sits on a consumer's default branch. The offline controls prove the verdict, the validator and the static guards, not the live API calls or the `job.workflow_*` context values. `actionlint` 1.7.7 does not yet know `job.workflow_repository` / `job.workflow_sha` and reports them.
* Callers pin the head SHA of the pull request branch that introduced this gate; merge that pull request with a merge commit, not a squash, so the pinned SHA stays reachable on `main`.

== Bootstrap

`workflow_run` and `schedule` run only from the default branch (and `workflow_dispatch` only for a workflow file that exists there). The pull request that adds a caller therefore never receives the gate status itself, and where the repository's ruleset requires that status the pull request can not merge until it is merged past the gate once. This applies to every consumer's bootstrap pull request and to the pull request that added the suite's own caller (`.github/workflows/ci-gate-caller.yml`, context `CI / gate`); the owner merges each of them past the gate once. After that merge the caller exists on the default branch and gates later pull requests.

== The suite gates itself

`.github/workflows/ci-gate-caller.yml` has the caller shape of the template, with the local reusable `./.github/workflows/ci-gate.yml` in place of the pinned remote one and the context `CI / gate`, the status context the suite's `main` ruleset requires. Its profile is `profiles/ci-gate/hyperpolymath/proven-cicd-and-workflows.json`, derived as recorded in link:../profiles/ci-gate/README.adoc[profiles/ci-gate/README.adoc]. Because the reusable is local, `job.workflow_repository` and `job.workflow_sha` are the suite and its own default-branch commit, so the profile and the scripts are read from the commit that runs; a pull request still can not change them before merge. The lock-scope guard (`scripts/check-workflow-lock-scope.sh`) accepts a local reusable workflow reference only when it names a plain file under `.github/workflows` that exists and is in `config/workflow-lock-scope.json`, and inspects that file's own references like any other workflow.
