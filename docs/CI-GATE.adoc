= Interim CI/gate

The Branch-Floor rulesets on `main` of some estate repositories require the commit-status
context `CI/gate`, and nothing emitted it. This is a swappable interim gate that does. A later
A3 `estate-gate` replaces it by changing one pin and one context name in each caller.

* Reusable: `.github/workflows/ci-gate.yml` (job id `gate`).
* Caller: `templates/ci-gate-caller.yml` (`__CICD_SUITE_SHA__`, DE-ONBOARDED from `actions.lock` like the Rust CI caller). The suite gates itself with `.github/workflows/ci-gate-caller.yml` (context `CI / gate`, the local reusable).
* API helper and status writer: `scripts/ci-gate-lib.sh` (every request, the back-off, the description sanitiser, the one status write).
* Publisher: `scripts/ci-gate-publish.sh` (one evaluation of one commit). Sweep: `scripts/ci-gate-sweep.sh`, run by the reusable on `schedule` and `workflow_dispatch`.
* Verdict (pure, offline): `scripts/ci-gate-verdict.sh`; the join of check runs to workflow runs `profiles/ci-gate/join-checks.jq`; profile validator `scripts/validate-ci-gate-profile.sh` with `profiles/ci-gate/validate.jq`.
* Required-check lists: `profiles/ci-gate/<owner>/<repo>.json`, derived as recorded in link:../profiles/ci-gate/README.adoc[profiles/ci-gate/README.adoc].
* Controls: `tests/ci-gate.sh` (run by the `Composite shell contract` job of `code-hygiene-self-test.yml`).

== Design in one paragraph

The caller starts `gate-pr` on `pull_request` for same-repository branches (see "Bootstrap" and "The pull_request start"). Its default-branch `gate` job triggers on `workflow_run` (types `completed`, `requested` and `in_progress`, any workflow but its own; a start event is let through only for a re-run, see "Re-runs"), on `schedule` (minutes 7, 22, 37 and 52 of every hour) and on `workflow_dispatch`; see "Sweep" below for the last two. Every evaluation reads the head commit with *two* requests, whatever the number of workflows: the workflow runs of the head SHA (`GET /repos/{repo}/actions/runs?head_sha=`) and the latest check runs of the commit (`GET /repos/{repo}/commits/{sha}/check-runs?filter=latest`), each over its pages of 100. The check runs are joined to their workflow run on check suite id (`check_suite_id` of the run, `check_suite.id` of the check run), which rebuilds the same per-job records the verdict has always read; the profile format and the verdict rules are unchanged except for the pending rules below. The reusable's job has a `concurrency` group keyed on repository, context and head SHA with `cancel-in-progress`, so the newest event for a commit replaces an evaluation of it that is still queued or running; the sweep has its own group. GitHub runs `workflow_run` workflows from the default branch, so a pull request cannot edit the caller, its pin or its list. The reusable reads the profile for `github.repository` from this suite at `job.workflow_sha`, runs the verdict script and posts one commit status. It is a commit status, not a check run, because a job in a reusable workflow gets the check-run name `<caller job> / <called job>`, which can never equal `CI/gate`.

*Why it works this way (resource-algebra#50).* One push started 22 workflows. The previous design started an evaluation per started and per completed workflow, and each evaluation listed the jobs of every run (one request per run), again on every poll of a waiting pull request, plus a sweep every 15 minutes. That exhausted the installation token quota (`HTTP 403 API rate limit exceeded`), after which the gate published a failure for a commit whose every required check had passed, and a status stands until something overwrites it. Reading in bulk and coalescing remove most of that load. Neither can promise that the API stays available, so an unavailable API now ends in `pending`, never in a failure.

== Verdict rules

Only GitHub Actions check runs are read. Third-party checks (SonarCloud, CodeRabbit, GitGuardian, CodeQL from github-advanced-security) are out of scope: their check runs belong to no workflow run's check suite, so the join drops them, and they are neither counted nor able to spoof a name.

. Workflow runs of the head commit are listed (all pages). The gate's own runs (by workflow name) are dropped; per (`workflow_id`, `event`) only the newest run (highest `id`) is kept. The latest check runs of the commit (`filter=latest`, all pages) are joined to their run, so an earlier attempt of a rerun is discarded and a check run of a run that was not kept is not counted. *Completeness of the bulk reads.* GitHub caps `actions/runs?head_sha=` at 1000 results, and the commit check-runs listing covers only the most recent 1000 check suites. Each listing reports a `total_count`. If that exceeds the items actually collected, the snapshot is *incomplete*: the read returns the unavailable path (exit 75, so `pending` and never a verdict, with `snapshot incomplete: ...` in the log), and omitted data is never treated as a missing check. Each page must also be exactly one JSON document of the expected shape: a blank, malformed or differently shaped 200 body is a real error (`unusable response body`), while a valid empty page is fine.
. A profile entry is an identity, `{job, workflow}` (profile `schema_version` 2): the job display name (the check-run name, `<caller job> / <called job>` for a job in a reusable workflow) and the workflow file (`path` of the run) (GitHub may report that path as `.github/workflows/build.yml@main`; an `@<ref>` right after the `.yml` or `.yaml` file name of a run path is ignored, the profile side never carries one, and distinct files stay distinct) that produces it. An entry is satisfied only if a kept run with that `path` exists and *every* check run with that exact `name` in those runs is `completed` with conclusion `success`. Two workflows producing one display name are two entries, both required. Two jobs that share a name inside one run are both required; none is chosen by highest `id`.
. Any required-name check run completed with another conclusion (`failure`, `cancelled`, `timed_out`, `skipped`, `neutral`, `action_required`, `stale`, none) is a *failure* at once. `skipped` and `neutral` are not passes. So is a kept run of a required workflow that completed unsuccessfully (`startup_failure`, `cancelled`, ...) and produced none of the entry's check runs.
. Else, if any workflow run of the commit other than the gate's own (kept or superseded, so a rerun of an older run counts) is still `queued`, `in_progress`, `waiting`, `requested` or `pending`, the verdict is *pending* (`waiting for N workflow runs: ...`), even when every required name already has a passing check run, because a later producer of the same name may still fail. Once the oldest kept or active run is older than `timeout_minutes` it is a *failure* (`timed out after N min: ...`). The clock starts at the creation of the oldest *eligible* run: the oldest kept or active workflow run that is not the gate's own. A superseded run that has completed does not start it, and a `CI gate` run alone never does. The timeout is applied by a later evaluation (the next `workflow_run` completion, `pull_request` event or sweep); nothing evaluates a commit by itself once the deadline passes.
. Else (nothing is active): an entry with no kept run or no check run, or whose check run has not completed, is *pending* (`not yet reported: <workflow file>:<job>`). There is no poll loop to wait it out: the next `workflow_run` completion or the sweep re-evaluates, and nothing bounds when that happens. Once the oldest eligible run of the commit (the oldest kept or active non-gate workflow run, as above; a `CI gate` run alone does not start the clock) is older than `timeout_minutes`, the verdict of a later evaluation becomes a *failure* (`never reported: ...`, `never completed: ...`), which is how a path-filtered or conditional required check (see "Known limits") still fails closed. If the commit has no workflow run at all there is no clock, and the verdict stays pending. Zero matched required checks is therefore never success. Otherwise the verdict is *success*.
. A malformed or wrong-repository profile, an empty list, a list naming the gate's own context, a missing `job.workflow_sha`, malformed input or API data, a real API error (a 4xx that is not a rate limit; a 403 that is a permissions problem, for example a caller that does not grant `checks: read`), or any event other than `workflow_run`, `pull_request`, `schedule` and `workflow_dispatch` is a failure, never pending and never success.
. An *unavailable* API is none of those: see "The API is rate-limited or unavailable".

The status description is at most 140 characters (see "Descriptions"); the step summary
carries the full table. `scripts/ci-gate-verdict.sh` exits 0 for success, 3 for pending and 1
for failure and for every error. It never sees the API.

== Publishing and the settle guard

Reading, evaluating and publishing is `scripts/ci-gate-publish.sh` (fetched from the suite at `job.workflow_sha` like the other scripts; it talks to GitHub only through `scripts/ci-gate-lib.sh`, which uses `gh`, so `tests/ci-gate.sh` drives it with a fake `gh`). It never waits for checks and never polls.

. On `pull_request` (and only there) it first writes one `pending` ("waiting for the required checks to report"), so a pull request without a verdict yet shows pending. It is de-duplicated like every write: nothing is posted if that exact status already stands. There is no pending write on any other event, except the single re-run pending of a re-run start event (see "Re-runs"). A first attempt's start events are filtered out at the caller. The initial `pull_request` pending is not an evaluation write: `published=true` is set only when the evaluation, or its error handler, writes a status.
. It snapshots the commit with the two reads and fingerprints the workflow runs: the sorted (`id`, `status`, `conclusion`, `run_attempt`, `updated_at`) of every run but the gate's own. It joins, and computes the verdict.
. Guard: just before the write it lists the workflow runs again (one request). If the fingerprint moved it does not write and starts a new round.
. Post-write verification: after the write it lists the runs once more. If the fingerprint moved since the snapshot it re-evaluates and writes again. On `pull_request`, when the write was `success`, it first writes `pending` ("runs still changing") so that no success stands while the next round evaluates (a bootstrap pull request has no default-branch evaluator to clear it). If that verification read is itself unavailable, the posted status stands, no recovery write is made, and the publisher reports `unavailable=true` (so a sweep stops), whether the posted state was `pending` or `failure`; an unverified `success` is replaced by the unavailable pending as before.
. At most 5 rounds are used. If the runs are still changing after 5 rounds, the last write is `pending` (`runs still changing`), never success. The guard and the verification apply to every state. They narrow, but do not close, the window in which a delayed evaluator leaves a stale state; see the residual limit below.
. A real error posts a failure status and exits non-zero. An unavailable API posts `pending` (below).

*Call budget.* A commit with fewer than 100 workflow runs and fewer than 100 check runs costs, in a round that settles, 6 requests: the runs and the check runs (the two reads), the runs again (guard), the combined status (the de-duplication read), the status write, and the runs again (verification), however many workflows there are; each further page of 100 adds one request to the read that has it. A round that does not settle repeats this, up to 5 rounds. The previous design added one request per workflow run to every snapshot and to every poll. `tests/ci-gate.sh` pins the count: 22 workflows cost the same requests as 2, there is no request to a jobs endpoint, and a snapshot is one request for the runs plus one per page of check runs.

*Coalescing.* The reusable's job is in the concurrency group `ci-gate-<repository>-<context>-<head SHA>` (the head SHA is `github.event.workflow_run.head_sha` or `github.event.pull_request.head.sha`) with `cancel-in-progress` for those two events: when several workflows of one push complete, or a pull request event follows a completion, the newest event replaces any evaluation of that commit still queued or running, so a burst costs a few evaluations instead of one per workflow. A cancelled evaluation may have been stopped between its guard and its write; the newest evaluation always reads fresh data, so this narrows the stale-write window and does not remove it. The sweep (`schedule`, `workflow_dispatch`) uses the group `ci-gate-<repository>-<context>-sweep` and is never cancelled: a sweep that runs longer than the 15-minute cron interval would otherwise be cancelled by the next one and never finish, and keeping it out of the per-commit groups means it neither cancels nor is cancelled by them. Two sweeps do not run at once: a running one finishes and one newer one waits. A caller needs no `concurrency:` block of its own, and the tests pin that the callers and the template have none.

== Re-runs (workflow_run start events)

The caller triggers on `workflow_run` types `completed`, `requested` and `in_progress`. A re-run has to flip a standing `success` to `pending` when it starts, but *which start event GitHub sends for a re-run is unconfirmed*: GitHub documents `requested` as not emitted for a re-run, and community reports agree, so `in_progress` is expected to be the event that does the work and `requested` is kept as a harmless extra. Both are subscribed so that the invalidation works whichever one GitHub really sends; `requested` can be dropped once live behaviour confirms it is never sent.

Both start events fire for first attempts as well, and a first attempt must not cost an evaluation each (one push once exhausted the API quota that way). The caller job's `if:` therefore admits `completed` always, admits `requested` or `in_progress` only when `github.event.workflow_run.run_attempt > 1` (a re-run), and keeps the gate's own workflow name out. Every first attempt is filtered before any job starts: it costs no runner and no API call. A skipped job still creates a workflow run record (the filter saves the runner and the requests, not the record).

For a re-run the reusable does not evaluate. It reads only `scripts/ci-gate-publish.sh` of the suite, and the publisher (`WORKFLOW_RUN_ACTION=requested` or `in_progress`, derived from `github.event.action` of the calling event) writes one `pending` ("ci-gate: a required workflow is re-running; re-evaluating on completion"), deduplicated by `gate_post` like every write, then exits. Its only requests are the status dedupe read and that one write: no run or check-run listing. If GitHub sends both start events for the same attempt, the second finds that pending standing: it makes the dedupe read and writes nothing. It never writes `failure` or `success` for a start event: a real error writes nothing (the next `completed` evaluation decides), and an unavailable API gets the same pending-only handling as elsewhere (exit 75, pending with the unavailable reason, never a failure). The profile is not read for it, so a missing profile is the completion's failure, not the start's.

Start events and `completed` evaluations of one commit share the per-SHA concurrency group with `cancel-in-progress`, so the newest event wins: a completion after the re-run starts supersedes the pending, and a start after a completion leaves `pending`. The race that remains is the one in "Residual limit": a status is last-writer-wins, so an evaluation of another workflow's completion that read the runs just before the re-run started may write its (stale) result after the re-run pending.

== The API is rate-limited or unavailable

Every request goes through one helper, `gate_api` in `scripts/ci-gate-lib.sh` (the one exception is the fetch of that file itself by the reusable's first step, which cannot use the helper it fetches and has its own bounded retry of 5 attempts at 5, 10, 20 and 40 seconds). It classifies each answer:

* 2xx: ok.
* HTTP 429, or 403 whose body says `rate limit` or whose `x-ratelimit-remaining` is 0 (a primary or secondary rate limit), any 5xx (`5xx`, so 505 too), or no HTTP answer at all: *unavailable*. The request is retried after `Retry-After` if the answer has it (decimal seconds, leading zeros stripped, bounded; or an HTTP-date in any of the three forms RFC 9110 requires recipients to accept, read in the C locale and converted to a delay: IMF-fixdate, RFC 850 whose two-digit year more than 50 years ahead is read as the most recent past year with those digits, and asctime; an invalid value is ignored), else, only when `x-ratelimit-remaining` is 0, until `x-ratelimit-reset` (an epoch timestamp of ten digits, parsed on its own with room for twelve), else, for a rate-limit 403 or 429 that still has budget and no `Retry-After` (a secondary limit), after 60 seconds doubling, else after an exponential delay (2, 4, 8, ... seconds, at most 60, plus jitter). A delay the server named is never shortened: if the remaining budget cannot cover it the call returns at once (75) with no early retry. A status write whose outcome is unknown (a 5xx or no answer) first rechecks the standing status and is not replayed if the status is already there; an explicit 429 or 403 rejection is retried.
* A 2xx whose body was cut off (`gh` printed 2xx headers but exited non-zero) is transient too: a read is retried within the budget, and a write is an unknown outcome, so the standing status is rechecked before any replay. A complete but malformed 2xx body is not: it is a real error.
* Anything else (404, 422, a 403 that is not a rate limit, an unusable body, missing credentials): a *real error*. It is not retried, and the evaluation fails closed (failure status, red job), as before.

The total time slept is bounded by `CI_GATE_BACKOFF_MAX_SECONDS` (default 300). A wait the answer already says would overrun the bound is not slept: the request gives up at once. A sweep shares one bound across all its publishers. When the bound is spent the status becomes `pending` with the description `ci-gate: GitHub API rate-limited or unavailable; re-evaluating later`, a `::warning::` is printed, the publisher exits 75 and the reusable's step ends green with that warning. *The gate never posts a failure because the API was unavailable.* If an evaluation had already written a `success` and cannot verify it, the success is replaced by that pending.

The pending write is retried with the same back-off under its own fresh budget, so one process may wait up to twice the bound. If that write is refused too, the job exits non-zero with a loud error saying that no status was written and no failure was posted. The earlier status then stands. The dedupe lookup of that write is a single attempt with no back-off, so it cannot spend the reserved budget; if it at once finds the same pending status the write is skipped.

The same holds in the reusable's profile-fetch step: an unavailable API there publishes the same pending (on `workflow_run` and `pull_request`) and skips the later steps; a missing profile or any real error fails closed through the fallback step, which posts the failure. A sweep that meets an unavailable API stops (the other heads would only meet it again), says in an `::error::` how many heads it did not evaluate and what is known of that head's pending write (written; rejected by GitHub; or *not confirmed*, because an unknown-outcome write may have landed; or, when only the post-write check was unavailable, that the posted status stands), and ends red; it writes no failure status. Its table headline counts the heads attempted, not the planned total. If the first step cannot read the library because the API is unavailable, nothing can be written through the library: the job is red, the step reports `unavailable=true` and no status is posted. If it cannot read it for any other (real) reason, the fallback step writes the failure with one small independent request (a fixed ASCII description, no library), so a standing success cannot survive.

None of this makes the API available. A pending status posted for an outage stands until the next `workflow_run` completion, a `pull_request` event or the sweep re-evaluates the commit; this design guarantees no time bound.

== Descriptions

Every status description is written by one function, `gate_post`, after one sanitiser, `gate_sanitize` (jq): it removes every codepoint above U+FFFF (the statuses API answers `Description doesn't accept 4-byte Unicode` for them; the shipped profiles contain a job named with an emoji, so this happened) and lone surrogates, and when more than 140 codepoints remain keeps 139 and appends an ellipsis, so it never cuts inside a character. BMP characters such as `é` and `✓` are kept. The fake API of `tests/ci-gate.sh` refuses 4-byte characters and over-long descriptions the way the real one does.

*Residual limit.* GitHub commit statuses are last-writer-wins and the statuses API has no compare-and-swap. A delayed evaluator can therefore publish a stale state, success included: one that was paused between its final check and its write overwrites a newer status. The guard, the post-write verification and the concurrency group shorten that window and do not remove it. This design guarantees neither convergence nor a time bound. Two stale outcomes remain possible. (1) Fail-open: a stale `success` stands until a later evaluator overwrites it; every completion of a workflow run raises a `workflow_run` event whose evaluator writes again, but nothing bounds when that happens. The start event of a re-run narrows the gap that removing the `in_progress` start events opened: a re-run replaces a standing `success` with `pending` when it starts. It is one more last-writer-wins writer: a `completed` evaluation of another workflow that read the runs just before the re-run was requested can still write a stale `success` after that pending, until the re-run's own completion evaluates. (2) Fail-closed: a delayed evaluator's final `pending` (for example "runs still changing", or the API-unavailable pending) can land after another evaluator's `success`, and if no workflow run changes afterwards it stays until the sweep, a `pull_request` event or a rerun evaluates again. Neither outcome is detected automatically. This is a residual limit of the interim gate, not something this design proves away. Removing it needs a compare-and-swap that the statuses API lacks; the A3 `estate-gate` design (signed envelopes) is the place to do that.

*The 1000-status cap and the dedupe.* GitHub keeps at most 1000 statuses per commit SHA and context; once a commit has that many, every further write for the context fails, the failure write of a failed run included. Every write (`gate_post`) therefore first reads the current status for the context (`GET repos/{repo}/commits/{sha}/status?per_page=100`, all pages, the combined status, which holds the latest status per context). If a status for exactly the gate's context already has the same `state` and the same `description` (compared after sanitising; `target_url` is not compared), the write is skipped, a `write skipped` line is logged, and the evaluation counts as published with the same exit code. If the read fails or is malformed, the gate writes anyway: it fails toward writing, never toward silence. This bounds the repetition of an unchanged verdict, the pending written first on `pull_request` included. It does not remove the cap: a head whose verdict keeps changing (a flaky required job, repeated re-runs, a sweep racing a `workflow_run` evaluator that flips `pending` and `success`) still adds one status per change and can reach 1000, after which the gate can no longer publish for that commit and the context is stuck at its last status.

== Sweep (schedule and workflow_dispatch)

On `schedule` and `workflow_dispatch` there is no triggering run, so the reusable sweeps `github.repository` instead of evaluating one commit. `scripts/ci-gate-sweep.sh` (fetched from the suite at `job.workflow_sha` like the other scripts; it uses only `gh` through `scripts/ci-gate-lib.sh`, so `tests/ci-gate.sh` drives it with the fake `gh`):

. lists the open pull requests (`/repos/{repo}/pulls?state=open&per_page=100`, every page) and the head of the default branch;
. de-duplicates the head SHAs (two pull requests with one head, or a pull request at the default branch head, are one evaluation);
. above 100 distinct SHAs it evaluates the 100 most recently updated, counting the default branch head as the most recently updated, and prints a `::warning::` naming how many were not evaluated; the step summary table names them too;
. runs exactly the guarded publisher (`scripts/ci-gate-publish.sh`) once per SHA, with no pending write first, so each SHA gets the same settle guard, post-write verification and fail-closed rules as a `workflow_run` evaluation; that includes the unchanged-status skip, so a sweep that finds an unchanged verdict writes nothing (the cap, "Residual limit");
. never stops on one SHA's failure or real error: it is recorded and the others are still evaluated. An unavailable API is the exception (see above): the sweep stops, names how many heads it did not evaluate, and ends red. This holds for a publisher that exits 75 and for one that hit the outage but could not write its pending either (it exits 1 but reports `unavailable=true` in its own `GITHUB_OUTPUT` file); the table and the error say whether the pending was written or its write failed. A discovery read (the repository, the default branch head, the pull request listing) that meets the outage stops the sweep at once, before any further call or publisher, and names the step and the heads found but not evaluated; any other discovery error keeps the partial discovery;
. writes a table (commit, source, state, description) to `$GITHUB_STEP_SUMMARY`, and exits non-zero at the end if any SHA ended in `failure`, `error` or `unavailable`, or if the pull request list or the default branch head could not be read. `pending` and `success` are not red.

The reusable accepts `workflow_run`, `pull_request`, `schedule` and `workflow_dispatch`; only the last two sweep. The job needs `pull-requests: read` in addition to `statuses: write`, `actions: read`, `checks: read` and `contents: read`: *the caller must grant them*, or the pull request listing or the check-run read fails. A sweep writes statuses for pull request heads from forks too (the statuses API is keyed by commit in the base repository); it reads metadata only and never checks out or runs their code.

== Workflow acceptance contract

|===
|Field |Statement
|Events |`workflow_run` (one commit; the caller triggers on types `completed`, `requested` and `in_progress`, and its job `if:` lets a start event through only for a re-run, `run_attempt > 1`), `pull_request` (the pull request head, through the same-repository `gate-pr` job), `schedule` and `workflow_dispatch` (a sweep of every open pull request head and the default branch head, at most 100 SHAs). Any other event is refused: red job, no status.
|Inputs |`context` (default `CI/gate`; the one swappable name; 1 to 128 characters: an alphanumeric first, then `[A-Za-z0-9._/-]` with single interior spaces, so `CI/gate` and `CI / gate` pass and a leading, trailing or repeated space, a tab or a newline does not; the regex `^[A-Za-z0-9]([A-Za-z0-9._/-]| [A-Za-z0-9._/-]){0,127}$` alone would admit up to 255 characters, so the length is checked separately; the validation step and the failure fallback carry the identical guard), `timeout_minutes` (default 180). `wait_minutes` and `poll_seconds` are *deprecated and ignored*: the `pull_request` start no longer waits or polls. They are still accepted so that callers pinned to an earlier commit keep working. The repository is never an input: the profile is selected by `github.repository`. No `secrets:`.
|Side effects |On `pull_request` one `POST /repos/{repo}/statuses/{head_sha}` of `pending` first (skipped if it already stands). Then a verdict write, repeated if the settle guard or the post-write verification finds the runs moved (at most 5 rounds, then `pending` "runs still changing"), with the context, state, a sanitised description (at most 140 characters, no codepoint above U+FFFF) and a `target_url` to the gate run, except that a write identical in context, state and description to the status already standing is skipped; each write is preceded by a read of the combined status of the commit; a step summary. When the API is rate-limited or unavailable beyond the back-off bound: one `pending` write instead, exit 75 (a warning, not a red job). Nothing else is written. Pending is a normal wait for the next `workflow_run` completion or the sweep. Concurrency group `ci-gate-<repository>-<context>-<head SHA>` with `cancel-in-progress` for `workflow_run` and `pull_request`, and `...-sweep` without it for the sweep.
|Permissions |Granted by the caller: `statuses: write`, `actions: read`, `checks: read`, `contents: read`, `pull-requests: read` (read only by the sweep). The reusable asks for exactly these and no more. GitHub does not let a called workflow ask for more than its caller grants, so a caller that does not grant `checks: read` is expected to fail to start (not exercised here, as no live caller exists yet).
|Subjects |The head commit of the triggering workflow run or pull request, in the repository the caller lives in. Required checks are Actions job names in the suite's profile for that repository. Third-party checks are out of scope.
|Failure and refusal |Any event other than `workflow_run`, `pull_request`, `schedule` or `workflow_dispatch`: refused, red job, no status. A sweep that ends with any SHA in failure, error or unavailable is red. A missing, empty, malformed, wrong-repository or self-naming profile, an empty `job.workflow_repository` or `job.workflow_sha`, or a real API error: failure; the job is red and a final step posts a failure status if none was published. A failed verdict also exits the job non-zero. An unavailable API is never one of these: it is `pending`. If neither the pending nor any other status can be written, the job is red and no status is posted. No code from the consumer or a pull request is checked out or executed, and no `${{ }}` reaches a `run:` script (values travel through `env:`).
|Controls |`tests/ci-gate.sh`: the context guard extracted from the workflow itself; the publisher end to end with the context `CI / gate`; the call budget (22 workflows cost the same requests as 2; no jobs endpoint; == Known limits

* Bootstrap: see "Bootstrap" below.
* A repository instantiated from the template gets the caller but no suite profile: the gate fails closed until a profile is added here.
* Anyone with write access can post a `CI/gate` status by hand; the rulesets do not pin an integration.
* A required check that is path-filtered or conditional does not report on a pull request that does not trigger it. It is `pending` until `timeout_minutes` after the oldest eligible run of the commit (the oldest kept or active non-gate workflow run; a `CI gate` run alone does not start the clock), and the failure, `never reported`, is written by the first evaluation after that deadline (the next completion, `pull_request` event or sweep), not by itself. Profiles list only checks that run unconditionally on both pull requests and pushes to `main`; re-derive a profile when a workflow's triggers change.
* A re-run flips a standing `success` to `pending` when it starts, through its start event (`requested` or `in_progress`; which one GitHub sends is unconfirmed, see "Re-runs"). First attempts are filtered at the caller job's `if:` before any job starts, so they cost no runner and no API call. The pending is last-writer-wins like every status; see the residual limit.
* A consumer that re-pins to this change must also grant `checks: read` in its caller (the gate now reads check runs) and set the `workflow_run` types of its caller to `[completed, requested, in_progress]` with the `if:` of `templates/ci-gate-caller.yml` (the `if:` is what keeps the start events of first attempts from evaluating). The consumer callers carry these types and the `if:` through their own re-pin pull requests, not through this change. `wait_minutes` and `poll_seconds` may stay or go.
* End-to-end behaviour on GitHub is not demonstrated until a caller sits on a consumer's default branch. The offline controls prove the verdict, the helper, the validator and the static guards against a fake `gh` that mimics the REST answers, not the live API calls, the `job.workflow_*` context values or the concurrency semantics. `actionlint` 1.7.7 does not yet know `job.workflow_repository` / `job.workflow_sha` and reports them.
* Callers pin the head SHA of the pull request branch that introduced this gate; merge that pull request with a merge commit, not a squash, so the pinned SHA stays reachable on `main`.

== Bootstrap

`workflow_run` and `schedule` run only from the default branch (and `workflow_dispatch` only for a workflow file that exists there). During bootstrap, the permanent `pull_request` path starts `gate-pr` from the pull request branch. It calls the reusable, posts `pending`, evaluates once and exits; it does not wait. A bootstrap pull request usually starts it before the other workflows have reported, so its status is `pending` ("not yet reported: ...") and, because the default branch has no `workflow_run` evaluator or sweep yet, nothing re-evaluates it by itself. Once the other checks have finished, re-run the `CI gate` workflow run of the pull request (a re-run of a `pull_request` run evaluates the same head again with the fresh check runs). A push is not a substitute: it starts a new head, which the same ordering can leave `pending` again. The status is posted on the pull request head (`CI/gate` for consumers, `CI / gate` for the suite). This is a consequence of removing the wait: the previous design polled for up to 50 minutes instead.

The caller must grant `statuses: write` and `checks: read`; a fork's or Dependabot's `pull_request` token cannot write statuses. The same-repository condition excludes forks, but does not grant a restricted token write access. Those pull requests depend on the default-branch `workflow_run` evaluator, which is unavailable until bootstrap is merged. After bootstrap, `workflow_run` evaluates later pull requests and reruns, including fork heads; `gate-pr` remains enabled for same-repository pull requests. Bootstrap does not make the pull request branch trusted: see "Tamper guard" below.

== The suite gates itself

`.github/workflows/ci-gate-caller.yml` has the caller shape of the template, with the local reusable `./.github/workflows/ci-gate.yml` in place of the pinned remote one and the context `CI / gate`, the status context the suite's `main` ruleset requires. Its profile is `profiles/ci-gate/hyperpolymath/proven-cicd-and-workflows.json`, derived as recorded in link:../profiles/ci-gate/README.adoc[profiles/ci-gate/README.adoc]. Because the reusable is local, `job.workflow_repository` and `job.workflow_sha` are the suite and the caller commit (the default branch for `gate`, the pull request merge commit for `gate-pr`), so the profile and the scripts are read from the commit that runs; the `pull_request` path can therefore change them before merge, which is why the tamper guard matters. The lock-scope guard (`scripts/check-workflow-lock-scope.sh`) accepts a local reusable workflow reference only when it names a plain file under `.github/workflows` that exists and is in `config/workflow-lock-scope.json`, and inspects that file's own references like any other workflow.

== The pull_request start

`workflow_run`, `schedule` and `workflow_dispatch` run only from the default branch, so on their own the gate can never run on the pull request that adds it, while a ruleset that requires the status blocks that very pull request. Every caller therefore also has a `gate-pr` job on `pull_request` (same-repository branches only: a fork's or Dependabot's `pull_request` token cannot write statuses; those are gated by the `workflow_run` job, which also re-evaluates after late workflows). It calls the same reusable and the same verdict; only the starting point and one extra write differ. This start is permanent.

* The reusable resolves the head SHA from `github.event.pull_request.head.sha` (or `workflow_run.head_sha`); any other event is refused.
* `gate-pr` is event-driven. It writes `pending` ("waiting for the required checks to report"; skipped if that exact status already stands), evaluates the commit once with the two reads, publishes the verdict, and exits. It does not wait and does not poll: `wait_minutes` and `poll_seconds` are ignored. The verdict of a pull request then comes from the `workflow_run` completions of its workflows (coalesced per head SHA) and, as a backstop, from the sweep. Neither is guaranteed to come at a particular time.
* The pending that `gate-pr` leaves is therefore normal when the other workflows are still running. The status never fails for that reason: a required check that has not reported is pending, and only past `timeout_minutes` a failure.
* No trust decision uses `github.actor` or any other forgeable field (Sonar S8232). The job runs only for same-repository pull requests by comparing the head repository with `github.repository`.

== Tamper guard

Because the `pull_request` job runs from the pull request's own branch, a pull request can edit the gate and pass itself. The tamper guard makes that visible: `.github/workflows/ci-gate-tamper-guard.yml` (reusable), called from a workflow on `pull_request_target`, which GitHub runs from the DEFAULT branch, so the pull request cannot edit the guard that judges it. It never checks out or runs pull request code. It reads the changed files (`previous_filename` of a rename included), the label events and the commit dates through the API (permissions `pull-requests: read`, `contents: read`; no secrets) and fetches its one script, `scripts/ci-gate-tamper-guard.sh`, from the suite at the pinned commit.

*Gate files:* `.github/workflows/ci-gate*.yml` and `.yaml` (callers, reusable, guard callers), `scripts/check-required-contexts.sh`, `scripts/ci-gate-*.sh`, `scripts/validate-ci-gate-profile.sh`, `templates/ci-gate*.yml`, `profiles/ci-gate/**`. A pull request that touches one fails the check `guard / check` unless the owner has applied the label `gate-change-approved` AFTER the pull request's newest commit.

*Approval, and who may give it.* The label is the owner's act. *Agents must never apply it.* It is re-checked on `labeled`, `unlabeled` and `synchronize`. The label is valid only if (a) its latest label event is `labeled`, (b) the actor of that event holds `admin` on the repository (`GET repos/{repo}/collaborators/{login}/permission` answers `.permission == "admin"`; a write or maintain actor, a deleted account, a bot, an unreadable or unexpected answer all refuse, and the check fails closed), and (c) that event is later than the newest commit date of the pull request, so the owner re-applies it after every push. The label name is the single `APPROVAL_LABEL` default in `scripts/ci-gate-tamper-guard.sh` (`gate-change-approved`; the owner has yet to confirm the final name); this document and the templates repeat it, and `tests/ci-gate-tamper-guard.sh` fails if they drift. Not verified live: that the `pull_request_target` token with `pull-requests: read` and `contents: read` may read the collaborator permission endpoint; if it may not, the guard fails closed for every gate-file pull request until the permission is granted.

*The limit, stated plainly.* A commit date is written by the pusher, and GitHub gives a read-only job no reliable push time, so a deliberate backdating or a force-push of older commits can defeat the comparison. And all agents act with the owner's account, so the label cannot tell the owner from an agent. This guard is tamper-EVIDENT and deliberate, not tamper-proof. A review-based approval is impossible because the owner cannot approve their own pull requests.

*Stronger form (proposed, not built).* Require commits that touch gate files to be signed by the owner's own key once the separate agent signing key exists, and have the guard verify the signer of each such commit from the API's `verification` data.

*Listing it in the profile.* The check is `{job: "guard / check", workflow: ".github/workflows/ci-gate-tamper-guard.yml"}` (suite local caller: `.github/workflows/ci-gate-tamper-guard-caller.yml`). It is NOT in any shipped profile yet, for two reasons that the owner should weigh: a `pull_request_target` workflow runs only from the default branch, so on the pull request that adds the guard the entry would read `never reported` and the gate would fail its own introduction; and a `pull_request_target` run's `head_sha` is not shown to be the pull request head, so whether the gate's per-commit run listing sees it is unverified. List it after the guard is on main and one later pull request shows its run in `actions/runs?head_sha=<head>`.

== What the owner must do once per repository

. Merge the pull request that adds the gate. The `gate-pr` job posts the status on it, so no ruleset edit is needed. If the pull request also touches gate files, the guard (once on main) will ask for the label.
. Apply the label `gate-change-approved` (create it once, colour free) to a pull request that touches gate files, after its newest commit, when you have read the change. Not an agent.
. After the guard workflow is on main, confirm on a later pull request that `guard / check` appears under `actions/runs?head_sha=<head>`, then add the profile entry above (a suite change that needs the label itself).
