= Interim CI/gate

The Branch-Floor rulesets on `main` of some estate repositories require the commit-status
context `CI/gate`, and nothing emitted it. This is a swappable interim gate that does. A later
A3 `estate-gate` replaces it by changing one pin and one context name in each caller.

* Reusable: `.github/workflows/ci-gate.yml` (job id `gate`).
* Caller: `templates/ci-gate-caller.yml` (`__CICD_SUITE_SHA__`, DE-ONBOARDED from `actions.lock` like the Rust CI caller). The suite gates itself with `.github/workflows/ci-gate-caller.yml` (context `CI / gate`, the local reusable).
* Sweep: `scripts/ci-gate-sweep.sh`, run by the reusable on `schedule` and `workflow_dispatch`.
* Verdict (pure, offline): `scripts/ci-gate-verdict.sh`; profile validator `scripts/validate-ci-gate-profile.sh` with `profiles/ci-gate/validate.jq`.
* Required-check lists: `profiles/ci-gate/<owner>/<repo>.json`, derived as recorded in link:../profiles/ci-gate/README.adoc[profiles/ci-gate/README.adoc].
* Controls: `tests/ci-gate.sh` (run by the `Composite shell contract` job of `code-hygiene-self-test.yml`).

== Design in one paragraph

The caller starts `gate-pr` on `pull_request` for same-repository branches (see "Bootstrap" and "The pull_request start"). Its default-branch `gate` job triggers on `workflow_run` (`completed` and `in_progress`, any workflow but its own), on `schedule` (minutes 7, 22, 37 and 52 of every hour) and on `workflow_dispatch`; see "Sweep" below for the last two. The `in_progress` event, which GitHub also sends when a run is rerun, makes the gate publish `pending` over a stale `success` while any run of the commit other than the gate's own is active (a rerun of an older, superseded run included), approximating a native required check; the evaluator triggered by `completed` then writes the verdict, subject to the residual last-writer-wins limit below. GitHub runs
`workflow_run` workflows from the default branch, so a pull request cannot edit the caller, its
pin or its list. The reusable reads the profile for `github.repository` from this suite at
`job.workflow_sha`, lists the workflow runs of the head commit (all pages), keeps the newest run per workflow and event without the gate's own, reads the jobs of the latest attempt of each, runs
the verdict script and posts one commit status. It is a commit status, not a check run,
because a job in a reusable workflow gets the check-run name `<caller job> / <called job>`,
which can never equal `CI/gate`.

== Verdict rules

Only GitHub Actions jobs are read. Third-party checks (SonarCloud, CodeRabbit, GitGuardian, CodeQL from github-advanced-security) are out of scope: they are neither counted nor able to spoof a name.

. Workflow runs of the head commit are listed (all pages). The gate's own runs (by workflow name) are dropped; per (`workflow_id`, `event`) only the newest run (highest `id`) is kept. For each kept run its jobs are read with `filter=latest` (all pages), so an earlier attempt of a rerun is discarded.
. A profile entry is an identity, `{job, workflow}` (profile `schema_version` 2): the job display name and the workflow file (`path` of the run) (GitHub may report that path as `.github/workflows/build.yml@main`; an `@<ref>` right after the `.yml` or `.yaml` file name of a run path is ignored, the profile side never carries one, and distinct files stay distinct) that produces it. An entry is satisfied only if a kept run with that `path` exists and *every* job with that exact `name` in those runs is `completed` with conclusion `success`. Two workflows producing one display name are two entries, both required, so a second producer that never ran is a failure. Two jobs that share a name inside one run are both required; none is chosen by highest `id`.
. Any required-name job completed with another conclusion (`failure`, `cancelled`, `timed_out`, `skipped`, `neutral`, `action_required`, `stale`, none) is a *failure* at once. `skipped` and `neutral` are not passes.
. Else, if any workflow run of the commit other than the gate's own (kept or superseded, so a rerun of an older run counts) is still `queued`, `in_progress`, `waiting`, `requested` or `pending`, the verdict is *pending* (`waiting for N workflow runs: ...`), even when every required name already has a passing job, because a later producer of the same name may still fail. Once the oldest kept or active run is older than `timeout_minutes` it is a *failure* (`timed out after N min: ...`).
. Else (nothing is active): an entry with no kept run or no job is a *failure* (`never reported: <workflow file>:<job>`), a required name whose job never completed is a failure, and otherwise the verdict is *success*.
. A malformed or wrong-repository profile, an empty list, a list naming the gate's own context, a missing `job.workflow_sha`, any API error, malformed input, or any event other than `workflow_run`, `schedule` and `workflow_dispatch` is a failure, never pending and never success.

The status description is at most 140 characters (truncated with an ellipsis) and never holds a 4-byte
UTF-8 character (any codepoint above U+FFFF, such as an emoji in a workflow or check name): GitHub rejects
those with "Description doesn't accept 4-byte Unicode", so they are stripped before truncation. The step summary
carries the full table. `scripts/ci-gate-verdict.sh` exits 0 for success, 3 for pending and 1
for failure and for every error.

== Publishing and the settle guard

Reading, evaluating and publishing is `scripts/ci-gate-publish.sh` (fetched from the suite at `job.workflow_sha` like the other scripts; it talks to GitHub only through `gh`, so `tests/ci-gate.sh` drives it with a fake `gh`). The caller has no `concurrency:` block: per-SHA serialisation would hold the `in_progress` caller behind a running evaluation that then writes a stale success.

. The first step after input validation, before any suite file is fetched, POSTs `pending` (`re-run started: <workflow name>`) when the event action is `in_progress`. It needs only `gh`, the repository, the head SHA and the context. Every later write is a fresh evaluation, so this early pending never hides a verdict.
. The publisher snapshots the workflow runs of the commit and fingerprints them: the sorted (`id`, `status`, `conclusion`, `run_attempt`, `updated_at`) of every run but the gate's own. It reads the jobs and computes the verdict.
. Guard: just before the POST it fetches the runs again. If the fingerprint moved it does not write and starts a new round.
. Post-write verification: after each POST it fetches the runs once more. If the fingerprint moved since the snapshot it re-evaluates and writes again.
. On `pull_request`, settling continues until the elapsed wait deadline and fails if runs remain unsettled. On other events, at most 5 rounds are used. If the runs are still changing after 5 rounds, the last write is `pending` (`runs still changing`), never success. The guard and the verification apply to every state. They narrow, but do not close, the window in which a delayed evaluator leaves a stale state (success, pending or failure); see the residual limit below.
. Any API or input error posts a failure status and exits non-zero.

*Residual limit.* GitHub commit statuses are last-writer-wins and the statuses API has no compare-and-swap. A delayed evaluator can therefore publish a stale state, success included: one that was paused between its final check and its POST overwrites a newer status. The post-write verification shortens that window and does not remove it. This design guarantees neither convergence nor a time bound. Two stale outcomes remain possible. (1) Fail-open: a stale `success` stands until a later evaluator overwrites it; every later change of a workflow run raises a `workflow_run` event whose evaluator writes again, but nothing bounds when that happens. (2) Fail-closed: a delayed evaluator's final `pending` (for example "runs still changing") can land after another evaluator's `success`, and if no workflow run changes afterwards it stays. The branch then remains blocked until someone re-runs a workflow on the commit, which raises a fresh evaluation. Neither outcome is detected automatically. This is a residual limit of the interim gate, not something this design proves away. Removing it needs a compare-and-swap that the statuses API lacks; the A3 `estate-gate` design (signed envelopes) is the place to do that.

*The 1000-status cap and the dedupe.* GitHub keeps at most 1000 statuses per commit SHA and context; once a commit has that many, every further write for the context fails, the failure write of a failed run included. The publisher used to POST on every evaluation, so a head that never changed would have used the cap up through the 15-minute sweep alone in about ten days. Every write (`post()`, `die()` included) therefore first reads the current status for the context (`GET repos/{repo}/commits/{sha}/status?per_page=100`, all pages, the combined status, which holds the latest status per context). If a status for exactly the gate's context already has the same `state` and the same `description` (compared after the 140-character clip; `target_url` is not compared), the POST is skipped, a `write skipped` line is logged, and the evaluation counts as published with the same exit code. If the read fails or is malformed, the gate writes anyway: it fails toward writing, never toward silence. This bounds the repetition of an unchanged verdict. It does not remove the cap: a head whose verdict keeps changing (a flaky required job, repeated re-runs, a sweep racing a `workflow_run` evaluator that flips `pending` and `success`) still adds one status per change and can reach 1000, after which the gate can no longer publish for that commit and the context is stuck at its last status. The early `pending` ("re-run started") of the first workflow step is not de-duplicated: it runs once per `in_progress` workflow-run event, so it is bounded by real workflow starts and re-runs, not by the clock; it must stay the first, read-free, unconditional step, and each such write is a genuine change of state (it replaces a standing verdict).

== Sweep (schedule and workflow_dispatch)

On `schedule` and `workflow_dispatch` there is no triggering run, so the reusable sweeps `github.repository` instead of evaluating one commit. `scripts/ci-gate-sweep.sh` (fetched from the suite at `job.workflow_sha` like the other scripts; it uses only `gh`, so `tests/ci-gate.sh` drives it with the fake `gh`):

. lists the open pull requests (`/repos/{repo}/pulls?state=open&per_page=100`, every page) and the head of the default branch;
. de-duplicates the head SHAs (two pull requests with one head, or a pull request at the default branch head, are one evaluation);
. above 100 distinct SHAs it evaluates the 100 most recently updated, counting the default branch head as the most recently updated, and prints a `::warning::` naming how many were not evaluated; the step summary table names them too;
. runs exactly the guarded publisher (`scripts/ci-gate-publish.sh`) once per SHA, with no early `in_progress` pending, so each SHA gets the same settle guard, post-write verification and fail-closed rules as a `workflow_run` evaluation; that includes the unchanged-status skip, so a sweep that finds an unchanged verdict writes nothing (the cap, "Residual limit");
. never stops on one SHA: a failure or an API error on one SHA is recorded and the others are still evaluated;
. writes a table (commit, source, state, description) to `$GITHUB_STEP_SUMMARY`, and exits non-zero at the end if any SHA ended in `failure` or `error`, or if the pull request list or the default branch head could not be read. `pending` and `success` are not red.

The reusable accepts `workflow_run`, `pull_request`, `schedule` and `workflow_dispatch`; only the last two sweep. The job needs `pull-requests: read` in addition to `statuses: write`, `actions: read` and `contents: read`: *the caller must grant it*, or the pull request listing fails and the sweep is red. A sweep writes statuses for pull request heads from forks too (the statuses API is keyed by commit in the base repository); it reads metadata only and never checks out or runs their code.

== Known limits

* Bootstrap: see "Bootstrap" below.
* A repository instantiated from the template gets the caller but no suite profile: the gate fails closed until a profile is added here.
* Anyone with write access can post a `CI/gate` status by hand; the rulesets do not pin an integration.
* A required check that is path-filtered or conditional would fail the gate as `never reported` on a pull request that does not trigger it. Profiles list only checks that run unconditionally on both pull requests and pushes to `main`; re-derive a profile when a workflow's triggers change.
* End-to-end behaviour on GitHub is not demonstrated until a caller sits on a consumer's default branch. The offline controls prove the verdict, the validator and the static guards, not the live API calls or the `job.workflow_*` context values. `actionlint` 1.7.7 does not yet know `job.workflow_repository` / `job.workflow_sha` and reports them.
* Callers pin the head SHA of the pull request branch that introduced this gate; merge that pull request with a merge commit, not a squash, so the pinned SHA stays reachable on `main`.

== Bootstrap

`workflow_run` and `schedule` run only from the default branch (and `workflow_dispatch` only for a workflow file that exists there). During bootstrap, the permanent `pull_request` path starts `gate-pr` from the pull request branch. It calls the reusable, waits within the configured budget for required checks, and publishes the required status on the pull request head (`CI/gate` for consumers, `CI / gate` for the suite). This lets a same-repository bootstrap pull request satisfy the gate before the caller reaches the default branch.

The caller must grant `statuses: write`; a fork's or Dependabot's `pull_request` token cannot write statuses. The same-repository condition excludes forks, but does not grant a restricted token write access. Those pull requests depend on the default-branch `workflow_run` evaluator, which is unavailable until bootstrap is merged. After bootstrap, `workflow_run` evaluates later pull requests and reruns, including fork heads; `gate-pr` remains enabled for same-repository pull requests. Bootstrap does not make the pull request branch trusted: see "Tamper guard" below.

== The suite gates itself

`.github/workflows/ci-gate-caller.yml` has the caller shape of the template, with the local reusable `./.github/workflows/ci-gate.yml` in place of the pinned remote one and the context `CI / gate`, the status context the suite's `main` ruleset requires. Its profile is `profiles/ci-gate/hyperpolymath/proven-cicd-and-workflows.json`, derived as recorded in link:../profiles/ci-gate/README.adoc[profiles/ci-gate/README.adoc]. Because the reusable is local, `job.workflow_repository` and `job.workflow_sha` are the suite and the caller commit (the default branch for `gate`, the pull request merge commit for `gate-pr`), so the profile and the scripts are read from the commit that runs; the `pull_request` path can therefore change them before merge, which is why the tamper guard matters. The lock-scope guard (`scripts/check-workflow-lock-scope.sh`) accepts a local reusable workflow reference only when it names a plain file under `.github/workflows` that exists and is in `config/workflow-lock-scope.json`, and inspects that file's own references like any other workflow.

== The pull_request start

`workflow_run`, `schedule` and `workflow_dispatch` run only from the default branch, so on their own the gate can never run on the pull request that adds it, while a ruleset that requires the status blocks that very pull request. Every caller therefore also has a `gate-pr` job on `pull_request` (same-repository branches only: a fork's or Dependabot's `pull_request` token cannot write statuses; those are gated by the `workflow_run` job, which also re-evaluates after late workflows). It calls the same reusable and the same verdict; only the starting point and one wait differ. This start is permanent.

* The reusable resolves the head SHA from `github.event.pull_request.head.sha` (or `workflow_run.head_sha`); any other event is refused.
* During bootstrap there is no default-branch `workflow_run` evaluator yet, and a `pull_request` run can start before the other workflows have created their runs. So `scripts/ci-gate-publish.sh` runs with `WAIT_SECONDS` (input `wait_minutes`, default 30, maximum 50 to reserve ten minutes of the 60-minute job for setup and final publication; `poll_seconds`, default 20): while the verdict only means "not finished" (`pending`, `never reported: ...`, `never completed: ...`) it polls without publishing the unfinished verdict, except that it replaces a success published by this invocation with pending if post-write verification detects changed runs. API calls and verdict evaluation count toward the elapsed wait budget; each sleep is capped at the time remaining. Completed-run jobs are cached within the publisher invocation while the run ID, attempt, status, conclusion and update time remain unchanged; active-run jobs are fetched on every poll. Before sleeping, the publisher reads the core API quota and increases the poll delay to spread estimated request costs over the reset window, reserving quota for final status publication. A real failure, and success, are written at once. When the wait is used up, `pending` becomes `failure: gave up after N min: waiting for ...`; `never reported` already names what is missing. The verdict script is unchanged; the wait keys on its descriptions, which `tests/ci-gate.sh` pins.
* The context stands `pending` ("waiting for the required checks to report") while it waits. On every other event `WAIT_SECONDS` is 0 and nothing changes.
* No trust decision uses `github.actor` or any other forgeable field (Sonar S8232). The job runs only for same-repository pull requests by comparing the head repository with `github.repository`.

== Tamper guard

Because the `pull_request` job runs from the pull request's own branch, a pull request can edit the gate and pass itself. The tamper guard makes that visible: `.github/workflows/ci-gate-tamper-guard.yml` (reusable), called from a workflow on `pull_request_target`, which GitHub runs from the DEFAULT branch, so the pull request cannot edit the guard that judges it. It never checks out or runs pull request code. It reads the changed files (`previous_filename` of a rename included), the label events and the commit dates through the API (permissions `pull-requests: read`, `contents: read`; no secrets) and fetches its one script, `scripts/ci-gate-tamper-guard.sh`, from the suite at the pinned commit.

*Gate files:* `.github/workflows/ci-gate*.yml` and `.yaml` (callers, reusable, guard callers), `scripts/check-required-contexts.sh`, `scripts/ci-gate-*.sh`, `scripts/validate-ci-gate-profile.sh`, `templates/ci-gate*.yml`, `profiles/ci-gate/**`. A pull request that touches one fails the check `guard / check` unless the owner has applied the label `gate-change-approved` AFTER the pull request's newest commit.

*Approval, and who may give it.* The label is the owner's act. *Agents must never apply it.* It is re-checked on `labeled`, `unlabeled` and `synchronize`. The label is valid only if (a) its latest label event is `labeled`, (b) the actor of that event holds `admin` on the repository (`GET repos/{repo}/collaborators/{login}/permission` answers `.permission == "admin"`; a write or maintain actor, a deleted account, a bot, an unreadable or unexpected answer all refuse, and the check fails closed), and (c) that event is later than the newest commit date of the pull request, so the owner re-applies it after every push. The label name is the single `APPROVAL_LABEL` default in `scripts/ci-gate-tamper-guard.sh` (`gate-change-approved`; the owner has yet to confirm the final name); this document and the templates repeat it, and `tests/ci-gate-tamper-guard.sh` fails if they drift. Not verified live: that the `pull_request_target` token with `pull-requests: read` and `contents: read` may read the collaborator permission endpoint; if it may not, the guard fails closed for every gate-file pull request until the permission is granted.

*The limit, stated plainly.* A commit date is written by the pusher, and GitHub gives a read-only job no reliable push time, so a deliberate backdating or a force-push of older commits can defeat the comparison. And all agents act with the owner's account, so the label cannot tell the owner from an agent. This guard is tamper-EVIDENT and deliberate, not tamper-proof. A review-based approval is impossible because the owner cannot approve their own pull requests.

*Stronger form (proposed, not built).* Require commits that touch gate files to be signed by the owner's own key once the separate agent signing key exists, and have the guard verify the signer of each such commit from the API's `verification` data.

*Listing it in the profile.* The check is `{job: "guard / check", workflow: ".github/workflows/ci-gate-tamper-guard.yml"}` (suite local caller: `.github/workflows/ci-gate-tamper-guard-caller.yml`). It is NOT in any shipped profile yet, for two reasons that the owner should weigh: a `pull_request_target` workflow runs only from the default branch, so on the pull request that adds the guard the entry would read `never reported` and the gate would fail its own introduction; and a `pull_request_target` run's `head_sha` is not shown to be the pull request head, so whether the gate's per-commit run listing sees it is unverified. List it after the guard is on main and one later pull request shows its run in `actions/runs?head_sha=<head>`.

== What the owner must do once per repository

. Merge the pull request that adds the gate. The `gate-pr` job posts the status on it, so no ruleset edit is needed. If the pull request also touches gate files, the guard (once on main) will ask for the label.
. Apply the label `gate-change-approved` (create it once, colour free) to a pull request that touches gate files, after its newest commit, when you have read the change. Not an agent.
. After the guard workflow is on main, confirm on a later pull request that `guard / check` appears under `actions/runs?head_sha=<head>`, then add the profile entry above (a suite change that needs the label itself).
